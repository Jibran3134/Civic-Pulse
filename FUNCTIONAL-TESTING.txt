0. THINGS THAT WILL WASTE YOUR TIME IF YOU DON'T KNOW THEM
--------------------------------------------------------------------------------

These cost real time to discover. Read this section first.

0.1  The request body field is "text", NOT "complaint".
     Contact is "reporter_contact" (a single free-text field), NOT
     "contact_name" / "contact_phone". There is no phone or email field.

0.2  The API prefix is /api, NOT /api/v1.

0.3  The status update route is PATCH /api/complaints/{id}/status
     PATCH /api/complaints/{id} returns 405 Method Not Allowed.

0.4  complaint_id must be a UUID. A malformed id such as 999999 returns
     400, not 404. A well-formed but absent UUID returns 404. Both are
     correct - test whichever you actually mean.

0.5  "outage" and "light" are keywords for BOTH electricity and
     streetlights, and "main" is a water keyword. The rules provider picks
     the highest keyword-score category, so wording decides the answer.
     See section 3 case 8, which lands on "water" because of the word
     "main" in "main valve". That is correct behaviour, not a bug.

0.6  There are TWO different caches. They are not connected:
       - the STATS read-through cache  -> reported by the X-Cache header
       - the TRIAGE content-hash cache -> reported by cache_stats in
                                          /api/meta/providers
     If you confirm X-Cache: HIT but cache_stats says hits: 0, there is no
     contradiction. See sections 6 and 7.

0.7  Ollama does not work in the Docker stack. The pinned image
     ollama/ollama:0.1.47 cannot load llama3.2:1b. Every Ollama call falls
     back to rules, so triaged_by reads "rules:fallback" and latency looks
     implausibly low. Full detail and fix in section 8.

3. TRIAGE / LLM - IS IT RETURNING A CORRECT RESPONSE?
--------------------------------------------------------------------------------

3.1  Which provider is active?

  curl http://localhost:8000/api/meta/providers

  Expected: "active_provider" matching what you configured
  Result  : PASS

  The compose stack ships TRIAGE_PROVIDER=simulated, so that is what you will
  see by default. simulated returns a fixed deterministic result and is the
  right choice for repeatable testing. For meaningful classification output
  set TRIAGE_PROVIDER=rules (deterministic keyword rules) or groq/ollama.

3.2  The response shape

  A 201 response contains all of these:

    {
      "id": "c1e6f62f-ab78-4fdd-a36d-b3ef6951b1e6",
      "text": "Emergency gas leak reported near the main valve",
      "location": "Saddar",
      "reporter_contact": "03001234567",
      "category": "water",
      "priority": "high",
      "status": "open",
      "ai_summary": "Emergency gas leak reported near the main valve",
      "triaged_by": "rules",
      "triage_latency_ms": 0,
      "created_at": "2026-09-27T16:26:49.515702Z",
      "updated_at": "2026-09-27T16:26:49.515702Z"
    }

    Check: category and priority are populated, ai_summary is non-empty,
    triaged_by names the provider that actually answered, and the response
    is 201 not 200.

3.3  THE COMPLAINTS TO SUBMIT, AND THE EXPECTED RESULT

  These 8 were run against the rules provider. Every result below is the
  actual observed output, not an inference.

  POST /api/complaints   for each:

  #  text                                                    location      EXPECTED              WAS
  -- ------------------------------------------------------- ------------- -------------------- --------
  1  Water pipe burst flooding the street                    Gulberg       water / high          water / high      OK
  2  Power outage in the whole colony since morning          Model Town    electricity/normal    electricity/normal OK
  3  Garbage not collected for three days, dumping smell     Johar Town    sanitation / normal    sanitation/normal  OK
  4  Large pothole on the road causing accidents             Cantt         roads / normal        roads/normal      OK
  5  Streetlight pole dark, no lighting at night             Shadman       streetlights / normal  streetlights/normal OK
  6  Broken park bench, minor cosmetic damage               Gulshan Park  other / low           other/low         OK
  7  No keywords whatsoever in this sentence at all          Somewhere      other / normal        other/normal      OK
  8  Emergency gas leak reported near the main valve         Saddar        water / high          water / high      OK

  Case 8 is the interesting one. "gas leak" has no category keyword, but
  "main" does, and "main" is in the WATER list - so it classifies as water.
  This is the rules provider working as designed (literal keyword scoring),
  not a misclassification. It is a good thing to be able to explain in the
  viva: it shows you understand the algorithm rather than just the output.

  Case 7 confirms the default: no category keywords -> other, no priority
  keywords -> normal. Neither is an error.

3.4  Confirm every response says triaged_by: "rules"

  If triaged_by says "rules:fallback" while TRIAGE_PROVIDER=rules, something
  is wrong with your rules provider. If you are on simulated you will get
  triaged_by: "simulated".

3.5  The field limits

    text              min 10 chars,  max 2000
    location          min  3 chars,  max  200
    reporter_contact  optional,     max  200

  Anything shorter must be rejected - see section 4.

6. CACHE 1 - THE STATS READ-THROUGH CACHE (X-Cache header)
--------------------------------------------------------------------------------

This is the one that matters for rubric section E.

  CACHE = HIT  when the answer came from Redis
  CACHE = MISS when it was recomputed from Postgres

6.1  Force a cold cache, then read three times

    docker exec civicpulse-redis redis-cli -n 0 FLUSHDB

    curl -i http://localhost:8000/api/stats | findstr /I "X-Cache"    -> MISS
    curl -i http://localhost:8000/api/stats | findstr /I "X-Cache"    -> HIT
    curl -i http://localhost:8000/api/stats | findstr /I "X-Cache"    -> HIT

  Expected: MISS, then HIT, HIT
  Result  : PASS (verified)

6.2  A write must invalidate the cache

    curl -i http://localhost:8000/api/stats | findstr /I "X-Cache"    -> HIT
    # now submit a new complaint
    curl -i http://localhost:8000/api/stats | findstr /I "X-Cache"    -> MISS
    curl -i http://localhost:8000/api/stats | findstr /I "X-Cache"    -> HIT

  Expected: HIT, then MISS, then HIT
  Result  : PASS (verified)

  This is the important one. Without invalidate-on-write, a freshly
  submitted complaint would not appear in /stats for up to 30 seconds.
  A read-through cache with a TTL but no invalidation is only half built.

6.3  TTL expiry alone also produces a MISS

    # STATS_CACHE_TTL defaults to 30
    curl -i http://localhost:8000/api/stats | findstr /I "X-Cache"    -> HIT
    Start-Sleep -Seconds 32
    curl -i http://localhost:8000/api/stats | findstr /I "X-Cache"    -> MISS

  Expected: MISS after ~30s with no write at all
  Result  : PASS (verified)

  Two independent mechanisms, as the code comment explains: the TTL bounds
  how stale the snapshot can ever be if an invalidation is lost, and the
  explicit invalidate-on-write makes a new complaint visible immediately.
  TTL alone shows operators stale data; invalidation alone leaks a stale
  entry forever if a future write path forgets to invalidate.

6.4  The stats payload shape

    {
      "by_category": {"water": 2, "electricity": 1, "sanitation": 1,
                      "roads": 1, "streetlights": 1, "other": 3},
      "by_priority": {"high": 2, "normal": 6, "low": 1}
    }

  Note there is no total_complaints key. Sum by_category if you need a total.

7. CACHE 2 - THE TRIAGE CONTENT-HASH CACHE
--------------------------------------------------------------------------------

A different cache from section 6, 24h TTL, keyed on a hash of the complaint
text. Reported by /api/meta/providers, NOT by an X-Cache header.

7.0  READ THIS FIRST - the POST response gives you NO signal either way

    A cache hit and a cache miss produce an IDENTICAL complaint body. Verified:

      HIT : triaged_by = "simulated", triage_latency_ms = 0
      MISS: triaged_by = "simulated", triage_latency_ms = 0

    triaged_by does NOT become "cache" on a hit. Looking at
    services/triage.py:107, a hit returns
    triaged_by=cached_data.get("triaged_by", "cache")
    -- that is the provider that produced the ORIGINAL result, so it still
    reads "simulated". The ".get(... , "cache")" default only applies if the
    cached entry has no triaged_by field at all, which never happens.

    And with TRIAGE_PROVIDER=simulated the provider is instantaneous, so
    latency is 0 on a hit AND on a miss. Latency is therefore worthless as a
    cache signal in the default configuration.

    THE ONLY TWO RELIABLE SIGNALS ARE:
      1. /api/meta/providers  ->  recent_outcomes[0].cache_hit  (true/false)
      2. /api/meta/providers  ->  cache_stats.cache_hits  (a rising counter)

    If you concluded the cache was broken from the POST response, it was not.

7.1  Submit the SAME text AND location twice, then compare

    The cache key is built at services/triage.py:38-41 as

        sha256( text.strip().lower() + "|" + location.strip().lower() )

    So BOTH text and location must match. reporter_contact is NOT part of
    the key.

    SAME = "Identical text submitted twice to prove the content hash cache hits"

    curl -X POST ... -d "{\"text\":\"<SAME>\",\"location\":\"Repeat Zone\"}"
    curl http://localhost:8000/api/meta/providers   -> recent_outcomes[0].cache_hit
    curl -X POST ... -d "{\"text\":\"<SAME>\",\"location\":\"Repeat Zone\"}"
    curl http://localhost:8000/api/meta/providers   -> recent_outcomes[0].cache_hit

  Expected: 1st = false, 2nd = true
  Result  : PASS (verified)

    POST #1: cache_hit=False  cache_hits 0 -> 0
    POST #2: cache_hit=True   cache_hits 0 -> 1
    POST #3: cache_hit=True   cache_hits 1 -> 2

7.2  The counter moves

    cache_stats = {"total_queries": 11, "cache_hits": 1,
                   "cache_misses": 10, "hit_rate": 0.0909}

  Expected: cache_hits rises by 1 and hit_rate becomes non-zero
  Result  : PASS (verified)

7.3  What causes a MISS - all five cases verified on the live stack

  Change                          cache_hit   why
  ------------------------------ -----------  ------------------------------
  same text, same location        false        first time, nothing cached
  same text, same location again  TRUE         identical key
  same text, DIFFERENT location   false        location is in the key
  same text+location, new contact TRUE         contact is NOT in the key
  same text, location only differs
    in case or surrounding spaces TRUE         .strip().lower() normalises
  one character changed           false        different SHA-256

  Case 4 is the one people trip on: changing only reporter_contact still
  HITS, because contact is not hashed. Case 3 is the opposite trap: the
  complaint reads as "the same report" but a different location is a
  different key.

7.4  Why your cache_stats may legitimately read hits: 0

  If every complaint you submitted had DIFFERENT text, every content hash is
  different and every lookup is a genuine miss. hits: 0 with misses: 9 is
  correct in that case. Only identical text AND location produces a hit.

  If you submitted the same complaint only ONCE, hits: 0 is also correct --
  a single lookup is necessarily a miss.

  This is the most likely thing to be misread as a broken cache. Section 6
  and section 7 are separate mechanisms; a HIT on one says nothing about the
  other.

8. OLLAMA PROVIDER - CURRENTLY BROKEN IN DOCKER
--------------------------------------------------------------------------------

This is a real defect in compose.yaml, not in the application code.

8.1  Symptom

    With TRIAGE_PROVIDER=ollama, every submission returns HTTP 201 with the
    correct category but:

      triaged_by      = "rules:fallback"
      triage_latency_ms = 0 to 7   (implausibly fast for any LLM)

    Backend log:
      {"message": "triage_fallback", "provider": "llm:ollama",
       "error_class": "HTTPStatusError"}

8.2  Root cause - confirmed, not guessed

    docker exec civicpulse-ollama ollama --version
      -> ollama version is 0.1.47

    curl http://localhost:11434/api/version        (host instance)
      -> {"version":"0.34.4"}

    The pinned image ollama/ollama:0.1.47 is far older than the host build
    and cannot read the current llama3.2 model format:

      llama_model_load: error loading model:
        done_getting_tensors: wrong number of tensors; expected 147, got 146

    Ollama server then returns HTTP 500:
      {"error":"llama runner process has terminated: signal: aborted"}

8.3  It is NOT a corrupt download and NOT a memory problem

    - ollama rm + ollama pull llama3.2:1b reports "success" and the failure
      reproduces identically. Two clean pulls, same tensor error.
    - docker stats civicpulse-ollama -> 82.51MiB / 4GiB (2.01%). Not memory.
    - The HOST ollama runs the same model fine:
        POST localhost:11434/api/generate -> HTTP 200 in 6899ms

8.4  How to verify the Ollama provider properly

  Option A - bump the image (recommended, and a genuine improvement):

    edit compose.yaml:  ollama/ollama:0.1.47  ->  ollama/ollama:latest
    docker compose up -d ollama
    docker exec civicpulse-ollama ollama pull llama3.2:1b

  Option B - run Ollama natively on the host, which already works, and point
  the backend at it:

    set TRIAGE_PROVIDER=ollama
    set OLLAMA_BASE_URL=http://host.docker.internal:11434
    set OLLAMA_MODEL=llama3.2:1b

8.5  What "correct" looks like once fixed

    triaged_by       = "llm:ollama"     (not "rules:fallback")
    triage_latency_ms = roughly 1000-8000 for a 1B model on CPU
    category/priority may legitimately differ from the rules provider -
      a 1B model is a weak classifier. That is expected and is precisely why
      RuleBasedTriage exists as the fallback.

8.6  Groq

  Not testable here: GROQ_API_KEY is empty. To test it you need Alishba's
  key in .env, then set TRIAGE_PROVIDER=groq and confirm triaged_by reads
  "llm:groq" with a latency in the hundreds of ms. Never commit the key.

9. STATUS WORKFLOW AND THE 409
--------------------------------------------------------------------------------

9.1  Get an id

    curl "http://localhost:8000/api/complaints?page=1&page_size=1"
    -> note the "id" field (a UUID)

9.2  Legal transitions must succeed

    curl -X PATCH http://localhost:8000/api/complaints/{id}/status ^
      -H "Content-Type: application/json" -d "{\"status\":\"in_progress\"}"
      Expected 200, status becomes in_progress          PASS

    curl -X PATCH http://localhost:8000/api/complaints/{id}/status ^
      -H "Content-Type: application/json" -d "{\"status\":\"resolved\"}"
      Expected 200, status becomes resolved             PASS

9.3  The illegal transition must be refused with 409

    curl -X PATCH http://localhost:8000/api/complaints/{id}/status ^
      -H "Content-Type: application/json" -d "{\"status\":\"open\"}"

  Expected 409, with the reason in the body:

    {"detail":"Invalid status transition from resolved to open. resolved is a
     terminal state; no further transitions are permitted."}

  Result: PASS (verified)

  The frontend is required to surface this message verbatim, so check the
  exact wording here first.

9.4  An invalid status VALUE is 400, not 409

    ... -d "{\"status\":\"not_a_status\"}"     Expected 400    PASS

  400 means the value is not a legal status at all. 409 means the value is
  legal but illegal from the current state. Keep them distinct.

      -e DATABASE_URL=postgresql://postgres:postgres@postgres:5432/civicpulse_test ^
